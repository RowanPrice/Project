# Architecture

```
                    reactorsim/  (pure Python, standard library only)
                    ┌───────────────────────────────────────────────┐
                    │  constants.py    physical + design data       │
                    │  neutronics.py   point kinetics, poisons      │
                    │  rods.py         bank worth and drives        │
                    │  thermal.py      primary, secondary, turbine  │
                    │  plant.py        reactivity balance, RPS      │
                    │  grid.py         demand, frequency, price     │
                    │  economy.py      contracts, ledger            │
                    │  research.py     enrichment, upgrades         │
                    │  storage.py      battery                      │
                    │  events.py       wear, faults, regulator      │
                    │  game.py         orchestration, actions       │
                    │  scenarios.py    starting conditions          │
                    │  web.py          Session: one game + history  │
                    └───────────────────┬───────────────────────────┘
                                        │  JSON
                        ┌───────────────┴───────────────┐
                        │                               │
                  app.py (Flask)                  docs/boot.js (Pyodide)
                  server + thread                 same package, in the tab
                        │                               │
                        └───────────────┬───────────────┘
                                        │
                              static/app.js + style.css
                              (identical in both)
```

## Layering

The rule is that dependencies point one way and `game.py` is the only module
that knows about all the others.

`constants.py` depends on nothing. `neutronics.py`, `rods.py` and `thermal.py`
depend only on constants — they are physics and know nothing about the game.
`plant.py` composes those three into a reactor and adds the reactivity balance
and the protection system; it still knows nothing about money. `grid.py`,
`economy.py`, `research.py`, `storage.py` and `events.py` are independent of
the physics and of each other. `game.py` wires everything together, owns the
clock, and exposes exactly two things to a front end: `state()` and
`act(action, payload)`.

Nothing in the physics imports Flask, and nothing in the physics imports
anything outside the Python standard library. That is not fastidiousness — it
is what lets the whole package run unmodified in the browser under Pyodide.

## Time

The plant is advanced by `Game.advance(seconds)`, which is called either by
`Game.tick(real_dt)` (wall clock × the speed multiplier) or directly.

There are three nested step sizes and each exists for a reason:

| Level | Step | Why |
|-------|------|-----|
| `Game.advance` | ≤ 30 s | Keeps the grid, economy and wear models linear over a step |
| `Plant.step` | ≤ 0.5 s | Everything in the plant has a time constant of a few seconds |
| `PointKinetics._step_explicit` | 20 µs | Only during a prompt excursion, where the period is milliseconds |

So running at 240× costs 8 plant sub-steps per 100 ms of wall clock, which is
a few milliseconds of CPU. The fast physics stays correct however fast the
clock runs, and the speed control is locked to 5× whenever the plant is in an
abnormal condition so that nobody fast-forwards through an accident.

## The two front ends

`reactorsim/web.py` holds a `Session`: one `Game`, the rolling trend buffer the
charts are drawn from, and a JSON API. Both front ends use it and neither adds
any simulation logic of its own.

**Flask** (`app.py`) wraps a Session in a lock and advances it on a daemon
thread at 20 Hz. The plant therefore keeps running whether or not a browser is
attached, which matters when the interesting dynamics take hours. HTTP handlers
only ever read a snapshot or post an action.

**The browser build** (`docs/`, generated by `tools/build_pages.py`) loads
Pyodide, writes the same `reactorsim/*.py` files into its virtual filesystem,
builds the same `Session`, and replaces `window.fetch` so that requests to
`/api/...` are answered by the in-page Python interpreter instead of by a
server. `static/app.js` is used **byte for byte identical** — it has no idea
which of the two it is talking to.

This is why GitHub Pages can host a Flask application's front end without a
Flask application: the simulation was never in Flask. Flask was one transport.

`tools/build_pages.py --check` fails if `docs/` has drifted from the sources,
and the test suite runs it.

## The interface

`static/app.js` polls `/api/state` at 4 Hz and re-renders. It holds no
simulation state of its own; every number on screen came out of the physics
this frame. Charts are drawn on canvas from the trend buffer the server sends.
There is no build step, no framework and no dependencies.

## Testing

144 tests in `tests/`, structured by what they are checking rather than by
module:

* `test_neutronics.py` — kinetics and poisons against published values: the
  55 second period at +100 pcm, the &minus;80 second negative asymptote, the
  prompt jump, equilibrium xenon at &minus;2700 pcm, the nine-hour post-trip
  peak.
* `test_thermal.py` — steam tables against the actual steam tables, Wigner-Way
  decay heat, and integrator stability at step sizes from 0.5 s to 120 s.
* `test_plant.py` — rod worth curves, the reactivity balance, every protection
  setpoint, the reactor-follows-turbine behaviour, the xenon pit blocking a
  restart, prompt criticality destroying the core.
* `test_economy.py` — separative work against published tables, contract
  settlement, market behaviour at both price extremes, battery round-trip
  efficiency.
* `test_game.py` — every scenario, every action, a week of unattended
  operation, and determinism from a seed.
* `test_web.py` — the shared Session, the JSON surface the browser build calls,
  and that `docs/` is in sync.

They are written as assertions about physics, not as regression snapshots. If
the model stops reproducing a textbook value the test fails, which is the point.

```
python3 -m pytest -q
```

## Adding to it

**A new reactivity effect** — add a term in `Plant.compute_reactivity`. It will
appear in the balance display automatically.

**A new trip** — add a row to the list in `Plant._standing_trip`. The delay,
the alarm, the log entry and the regulator's opinion are handled.

**A new upgrade** — add an `Upgrade` to `UPGRADE_CATALOGUE` in `research.py`
with its effect keys, and read the modifier where it applies. Add the default
to `DEFAULT_MODIFIERS`.

**A new contract product** — add a `kind` to `Contract.required_mw` and
`Contract.settle`, and an entry in `contract_catalogue`.

**A new scenario** — write a setup function in `scenarios.py` and add it to
`SCENARIOS`. `_settle(plant, target_power)` will find the boron concentration
that puts the plant steady at any power you ask for.

After changing anything under `reactorsim/`, `static/` or `templates/`, run
`python3 tools/build_pages.py` so the browser build keeps up.
